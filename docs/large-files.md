# 大文件自动接收与兼容分卷还原

v1.4 取消旧版文件原始总量 20 MiB / ZIP 25 MiB 的限制。单文件按 1 MiB 块读取并校验，不把几 GB 一次读进 JavaScript 内存；大文件夹使用 PAX TAR 保留目录、Unicode 文件名、原字节和逐文件 SHA-256，原文件数据通过 Blob / File 引用组成文件包。

[查看超过 2 GiB 文件的界面](images/large-file.png)。大文件测试会创建并在结束后删除一个 2 GiB + 129 字节的临时文件，运行测试时需留出几 GiB 的磁盘空间。

## v1.5 自动接收

1. 电脑选择或拖入文件，点击“准备发送”。超过 8 MiB 时自动生成 8 MiB 数据块；界面显示总块数及当前块号。
2. 手机在系统浏览器打开 [扫码桥接收页](https://1CWwW.github.io/scan-bridge/receiver/)，点击开启相机。相机与写盘能力须通过页面检测。
3. 电脑点击开始传输，手机对准完整彩色码。每块经过校验后自动写入磁盘，不弹出逐卷下载。
4. 手机提示已写入后，电脑点击下一块；播放中切块会继续发送。也可选定时循环（默认每块 180 秒），但定时器无法知道手机是否完成，需要按实际速度调整。漏块按接收页显示的块号补扫。
5. 收齐后自动计算整文件 SHA-256，通过校验才启用“保存完整文件”。保存到“文件”App / 下载目录并确认成功，再清除接收任务。

接收页将每块写到 OPFS `payload.bin` 的对应偏移，写后回读校验，提交小型块日志；只有数据与日志持久化后才增加进度。刷新时重读日志并复核磁盘内容，损坏或未提交的块会显示为缺失。重复块去重，不同文件拒绝混入。整个接收任务使用一个写入锁，避免多个接收页同时修改文件。只处理一个活动文件，接收其他文件前请保存并清除当前任务。

导出使用磁盘 File 或流式复制，不将完整的大文件读成 ArrayBuffer，也不在最后把所有块拼成一个巨大的内存数组。协议没有设置几百 MB 或 2 GB 总量限制，仍受浏览器配额、磁盘和最终下载能力限制。iPhone / 其他手机的多 GB 最终下载尚需实机验证。

重新选择完全相同的原文件后，整文件摘要和数据块划分不变，可跳转补扫。归档请先保存 ZIP / TAR，后续选择该归档作为单文件继续，避免重新打包的元数据改变摘要。

## 兼容旧接收器

上游 CIMBAR / CFC 不具备扫码桥的持久接收功能，需要逐卷接收并保存 `.sbpart`。使用“保存当前卷”也能直接导出兼容格式。下面的独立还原工具仅用于这种旧流程；它们的内存限制不适用于新的自动接收页。

`.sbpart` 是带有原文件名、大小、偏移、卷号、块摘要和整文件摘要的数据块封装，不是通用 ZIP 分卷，不能直接 `cat` 拼接整个文件。新接收页继续兼容 v1.4 的 8 MiB 数据块，应用层协议标识仍为 `scanbridge-part-1`。本次升级的是接收会话、磁盘持久化和完整文件导出，没有修改 CIMBAR 的物理编码格式或扩大其单流极限。

## 还原

从同一个 Release 下载 `merge-parts.html`，在目标电脑 Chrome/Edge 打开，选择全部分卷（顺序不限），点击还原并选择输出文件。工具逐卷验证、逐卷写盘，整文件校验通过后提交结果；损坏、缺卷、重复、混用或取消时不提交临时输出。

没有流式写盘能力的浏览器只支持 128 MiB 内存合并。尤其是几 GB 文件，不应假设手机浏览器可以完整合并；手机可以分卷保存，最后交给电脑或兼容运行环境中的 Python 工具。手机本地 HTML 的打开方式也可能限制脚本运行。

标准库 Python 3.10+ 工具不依赖浏览器：

```sh
python merge-parts.py 接收到的分卷文件夹 --output 还原后的文件.zip
```

也可以在命令后逐个列出 `.sbpart`。省略 `--output` 时使用卷内原文件名，工具拒绝覆盖已有文件。输出目录必须已存在，并留有足够磁盘空间。还原为 TAR / ZIP 后，再用支持该格式的工具解压；手机内置解压工具不一定支持 TAR。

## 容量和速度

总文件大小不再由扫码桥固定在 20 MB 或 2 GB。具体上限仍受浏览器的 File / Blob 能力、文件系统、磁盘空间和接收设备限制。JavaScript 卷位置使用安全整数，不通过 32 位位运算处理文件偏移。

每批最多 5000 个原文件。小批量 ZIP 是内存压缩，只处理 64 MiB 以内原始数据；更大批量默认使用 TAR。TAR 不压缩，体积通常接近原始内容。若想先压缩大文件夹，用系统归档工具制作 ZIP / 7z 再拖入传输。大 TAR 不生成可选全文摘要，但保留所有原文件与校验清单。

光学传输的速度不会随容量上限提高。举例：若真实有效吞吐量为 100 KiB/s，2 GiB 纯数据需约 5.8 小时，20 KiB/s 则约 29 小时，冗余帧、存盘和切卷还会增加时间。需要快速传几 GB 时，扫码通常不是合适的主传输方式。

单次 CIMBAR 流仍有限，扫码桥不修改上游编解码二进制，而把大文件拆为安全大小的独立流。上游格式说明见 [libcimbar](https://github.com/sz3/libcimbar)，浏览器写盘能力见 [Chrome File System Access 文档](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)。真实手机完整光学链路尚需实机测试。
