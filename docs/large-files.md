# 超过 2 GB 的文件与分卷还原

v1.4 取消旧版文件原始总量 20 MiB / ZIP 25 MiB 的限制。单文件按 1 MiB 块读取并校验，不把几 GB 一次读进 JavaScript 内存；大文件夹使用 PAX TAR 保留目录、Unicode 文件名、原字节和逐文件 SHA-256，原文件数据通过 Blob / File 引用组成文件包。

[查看超过 2 GiB 文件的界面](images/large-file.png)。大文件测试会创建并在结束后删除一个 2 GiB + 129 字节的临时文件，运行测试时需留出几 GiB 的磁盘空间。

## 发送

1. 选择文件，或拖入文件夹，保持“自动”处理方式，点击“准备发送”。准备过程会完整读取并计算校验值，可取消。
2. 待传内容超过 16 MiB 自动切为每卷最多 8 MiB 的 `.sbpart`。界面显示总卷数和当前卷号。
3. 手机打开 CIMBAR 接收端，电脑开始播放当前卷，等手机接收完成并保存。
4. 点击下一卷，重新开始播放。可重扫、上一卷或按卷号跳转；电脑无法知道手机是否保存成功，不会定时自动换卷。
5. 接收端收齐全部卷，再还原。原始大小、文件名、位置、每卷校验值和整文件校验值均包含在卷头内。

重新选择**完全相同**的原文件时，整文件摘要和卷划分不变，可以跳到未收齐卷号继续。重新生成的多文件归档可能有不同元数据；重启前最好先保存生成的 ZIP / TAR，再选择这一归档作为单文件继续。不要混用不同版本的卷。

“保存当前卷”可导出当前 `.sbpart`。它不是原文件，也不是通用 ZIP 分卷，不能直接用 `cat` 拼接整个卷文件。

## 还原

从同一个 Release 下载 `merge-parts.html`，在目标电脑 Chrome/Edge 打开，选择全部分卷（顺序不限），点击还原并选择输出文件。工具逐卷验证、逐卷写盘，整文件校验通过后提交结果；损坏、缺卷、重复、混用或取消时不提交临时输出。

没有流式写盘能力的浏览器只支持 128 MiB 内存合并。尤其是几 GB 文件，不应假设手机浏览器可以完整合并；手机可以分卷保存，最后交给电脑或兼容运行环境中的 Python 工具。手机本地 HTML 的打开方式也可能限制脚本运行。

标准库 Python 3.10+ 工具不依赖浏览器：

```sh
python merge-parts.py 接收到的分卷文件夹 --output 还原后的文件.zip
```

也可以在命令后逐个列出 `.sbpart`。省略 `--output` 时使用卷内原文件名，工具拒绝覆盖已有文件。输出目录必须已存在，并留有足够磁盘空间。还原为 TAR / ZIP 后，再用支持该格式的工具解压；手机内置解压工具不一定支持 TAR。

## 容量和速度

总文件大小不再由扫码桥固定在 20 MB 或 2 GB。具体上限仍受浏览器的 File / Blob 能力、文件系统、磁盘空间和接收设备限制。JavaScript 卷位置使用安全整数，不通过 32 位位运算处理文件偏移。

每批最多 5000 个原文件。小批量 ZIP 是内存压缩，只处理 64 MiB 以内原始数据；更大批量默认使用 TAR。TAR 不压缩，体积通常接近原始内容。若想先压缩大文件夹，用系统归档工具制作 ZIP / 7z 再拖入传输。大 TAR 不生成可选全文摘要，但保留所有原文件与校验清单。

光学传输的速度不会随容量上限提高。举例：若真实有效吞吐量为 100 KiB/s，2 GiB 纯数据需约 5.8 小时，20 KiB/s 则约 29 小时，冗余帧、存盘和切卷还会增加时间。需要快速传几 GB 时，扫码通常不是合适的主传输方式。

单次 CIMBAR 流仍有限，扫码桥不修改上游编码二进制，而把大文件拆为安全大小的独立流。上游格式说明见 [libcimbar](https://github.com/sz3/libcimbar)，浏览器写盘能力见 [Chrome File System Access 文档](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)。真实手机完整光学链路尚需实机测试。
