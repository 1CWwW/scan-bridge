# 接收页与自托管

默认入口：[扫码桥大文件接收页](https://1CWwW.github.io/scan-bridge/receiver/)。iPhone 推荐 Safari，Android 推荐支持相机与 OPFS 的新版系统浏览器。首次完整加载后，Service Worker 会缓存页面和编解码资源，可在离线状态下重开。文件内容只通过相机接收和本机写盘，程序不上传接收数据，不含统计或第三方脚本。

发送端依旧是离线单文件 HTML。接收端是 `dist/receiver/` 目录，包含网页、两个 Worker、协议和哈希库、WASM 解码器、离线缓存及许可证。相机和浏览器文件系统要求安全上下文，不能承诺手机直接打开 `file://` HTML 即可运行。

## 使用固定 1.5.2 接收页

[打开固定 1.5.2 接收页](https://1cwww.github.io/scan-bridge/receiver-v1.5.2/)。手机使用原来的浏览器普通模式，先关闭其他扫码接收标签页。电脑发送端无需降级；在“自托管接收地址”填入 `https://1cwww.github.io/scan-bridge/receiver-v1.5.2/` 并更新二维码，也能用手机扫码打开此版本。

该目录固定保存 v1.5.2 的 `receiver.js`、`decoder-worker.js` 和 `receiver-store.js`，校验值记录于 `source/pinned/1.5.2/manifest.json`，构建时逐文件检查。只有页面的固定版本提示和 Service Worker 缓存命名隔离有调整。其程序缓存使用 `scan-bridge-pinned-1.5.2-`，不会与默认接收页互相清除；接收数据仍使用同一来源下的 `scan-bridge-recv-v1/`，已写盘块可跨版本恢复，未完成块需重扫。两个接收页仍受同一单写入锁保护。

固定页不会跟随默认接收页升级。自托管时将 `dist/receiver-v1.5.2/` 整个目录部署到 HTTPS；它无需依赖默认接收页，保留所附许可证。普通模式和无痕模式的数据相互隔离，固定旧版不解决浏览器本身的权限或存储限制。

## 普通模式刷不掉旧版本

在原来的浏览器普通标签页打开 [更新入口](https://1cwww.github.io/scan-bridge/update-receiver.html)，先暂停扫描并关闭其他接收标签页，再点击“检查并更新程序”。确认新版本激活后点击“进入接收页”。原来的已写盘完整块会复查恢复，未完成块需重扫。无需清除 Safari 网站数据。

旧版离线缓存优先返回页面，还会忽略查询参数，所以反复刷新或添加 `?v=` 不能可靠升级。更新入口位于 `receiver/` 以外，获取新版本元数据后注册带版本及构建标识的新 Worker 地址；新版缓存按资源摘要区分构建，并通过 Worker 消息确认实际激活的版本。下载失败保留原缓存，允许重试。更新只处理程序缓存，不访问接收 OPFS 文件，也不删除其他缓存和网站状态。

灰色相机按钮表示接收存储检查尚未成功，程序没有申请相机权限。新版展示初始化状态及错误原文，后台连续 20 秒没有响应时提示重新检测；恢复进度持续更新时不设置 20 秒总时限。使用普通模式，并关闭提示占用存储的其他接收页；无痕存储限制、Worker 不可用等不会伪装成权限问题。

## 自托管

将发行包 `scan-bridge-v1.5.3-receiver.zip` 解压后的 `receiver/`、`update-receiver.html` 和 `receiver-version.json` 一起部署到静态 HTTPS 服务器，保持相对路径，并为 `.wasm` 提供 `application/wasm`。不需要数据库、上传接口、账户或跨源隔离响应头。首次加载的所有资源均来自同一站点。

电脑发送页“自托管接收地址”中填写新的 HTTPS 网址，更新接收二维码即可。每个来源有独立浏览器存储；更换网址来源、清除网站数据或使用另一个浏览器都不会自动带走当前接收进度。请先在原接收页保存文件。

在电脑本机测试可使用 Python 标准库：

```sh
python3 -m http.server 8000 --directory dist
```

本机访问 `http://localhost:8000/receiver/`。手机通过电脑局域网 IP 访问普通 HTTP 通常无法申请相机权限；手机使用应部署有效 HTTPS。

仓库的 `Publish receiver` 工作流会在主分支三平台验证通过后部署 GitHub Pages。自行 Fork 时需要启用仓库 Pages、选择 GitHub Actions，并将发送端默认网址改成自己的站点。

## 存储与恢复

一个接收任务使用浏览器 OPFS 中的 `scan-bridge-recv-v1/`，包含 `payload.bin` 和已提交数据块的小型 JSON 日志。输入的原文件名只作为下载名称，不用于构造本地目录。每块先验证摘要、写入并 flush、回读校验，再提交块日志；异常写入长度不会计为完成。

刷新会复查日志对应的磁盘数据。未提交、撕裂或损坏的块将重新显示为缺失。全部收齐后，完整文件长度和 SHA-256 必须匹配才允许导出。浏览器清理网站数据仍可能删除整个任务；“保留接收进度”只是向浏览器申请持久存储。

电脑 Chrome/Edge 可选择输出文件并流式复制。没有保存选择器的浏览器使用 OPFS 磁盘 File 的下载链接；不创建全文件 ArrayBuffer。系统的最终下载行为、额外磁盘空间需求以及手机多 GB 导出仍需设备实测。确认导出成功后再清除任务。

底层仍采用独立 8 MiB CIMBAR 流，接收器在每个流落盘后重建解码器，释放内存并避免长任务中的上游 7 位编码 ID 回绕干扰。定时循环只有单向传输，没有手机接收确认；漏块按提示重播。

该实现提高的是接收容量和完整文件的使用体验，不增加光学带宽。例如有效速度为 100 KiB/s 时，200 MiB 纯数据约需 34 分钟，2 GiB 约需 5.8 小时，实际还会有冗余、定位和重扫开销。

## 当前数据块进度慢时

先保持同一块，不要在未收齐时定时切走。90 MiB 文件会有 12 个数据块，默认每个 8 MiB；当前块条表示喷泉码解码器的估计进度，整文件条只累计已校验并写盘的原始字节，二者不同。5 FPS 表示电脑每秒仅输出约 5 张新画面，不是手机每秒能有效接收的保证。

先全屏显示电脑彩色码，保留四角、保持对焦、避免反光和抖动。若画面清晰，尝试从 5 FPS 提到 10 FPS；有码帧比例明显下降则退回 5 FPS。不要在未观察效果时直接使用最高帧率。云桌面画面如果经过缩放或压缩，也可能影响小格子和颜色的可辨认程度，需要在实际显示环境测试。

v1.5.3 接收页显示最近三秒的采集采样率、处理帧率、提交 / 返回总数、有码帧比例、解码耗时及处理尺寸。兼容采集的帧率是采样次数，不保证摄像头每次都提供了新画面。有码帧也可能包含重复内容，不等于文件净吞吐量。连续 15 秒无新增恢复进度时会单独提示；超过 3 秒没有解码返回时，不再沿用“正在恢复”的旧提示。这些诊断仅在本机计算。

- **采集和处理都为 0**：相机未提供可读画面，或采集通知停滞。自动模式在新帧通知超过约 1.2 秒不更新时回退，也可手动选择“兼容采集”。预览若冻结，暂停后重新开启相机。
- **已提交大于已返回，处理为 0**：正在等待解码器。超过 3 秒显示等待时间，单帧超过 30 秒停止并提示重扫当前块，已写盘完整块保留。
- **处理正常，有码帧少**：检查清晰度、四角、全屏与对焦。不要靠不断提高发送 FPS 解决。
- **处理和识别正常，当前块增加慢**：有效新码图数量不足、存在重复或数据压缩率低。源码 / 文本通常能压缩很多；ZIP、视频等常无法明显再压缩。

自动采集优先采用视频新帧通知和 presentedFrames；时间戳为零时仍能继续。回调缺失或计数停住时，改用独立的 67 毫秒兼容采样，不依赖可能冻结的视频计数器。解码器忙时只保留最新采样标记，不排队堆积图像。视频尺寸没变时复用画布缓冲。偶尔提取失败保留上次块进度。

暂停 / 暂时进入后台后，只要页面未被系统重载，重新开启相机可接着当前块扫描；切换采集方式也不重建解码器。电脑必须保持同一块且不要停止后重新编码。刷新、关闭页面、解码器错误仍需重扫未完成块；已校验写盘块会恢复。

完整随机数据测试：一个 8 MiB + 协议头的数据块，经过真实 CIMBAR 编码、1080 × 1920 画布和原版解码器，约 1,131 张有效码图后完成，SHA-256 与源封装相符。5 FPS 下仅有效码图就约需 226 秒；90 MiB 接近 43 分钟，实际手机丢帧会更久。此结果来自合成画面，不包含手机相机失真、云桌面显示损失，也不是设备吞吐量承诺。旧版主要测试的源码 / 文本和重复字节样例不能代表不可压缩数据。

定时切换默认从 180 秒改为 600 秒，避免在理论接收时间之前切走。600 秒仍不能保证完成；建议等手机提示当前块写盘后手动切换。

视频新帧接口见 [MDN requestVideoFrameCallback](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)；独立有效图像与喷泉码恢复的关系见 [libcimbar v0.6.8](https://github.com/sz3/libcimbar/tree/v0.6.8)。

升级缓存会重新获取同版本资源，避免新页面混用 HTTP 缓存中的旧脚本；测试覆盖旧 HTML / JS 仍在一年有效期缓存内的升级与离线重开。
